# Member service RPC contract

> 기본 관리자·공개 게시판 및 이전 인증 회원 API의 계약입니다. 현재 회원 화면의 신청·건의·접수 조회는 별도 `guest_service`를 사용하며, 회원 계정이나 초대 연결을 요구하지 않습니다. 최신 흐름은 [비로그인 접수 운영 안내](guest-service-operations.md)를 참조하세요.

All calls: `supabase.rpc('member_service', { action, payload })`. Successful JSON includes `ok:true`. Validation/authorization uses PostgreSQL errors (`error.message`). Invite failures return `{ok:false,error}` so rate-limit attempts persist; clients must check both transport errors and `ok`.

Program-specific form/term selection, signature modes and payment policy follow [프로그램별 신청서 계약](program-forms-contract.md). `public_home` additionally returns `forms` and `form_programs`; terms include `program`. New application payment methods are `card | transfer`. Existing `cash` records and snapshots remain readable and processable.

Online application creation accepts only `kind:'renewal'`. First-time users complete the paper form at the front desk. Historical `new` applications keep receipt, idempotent replay and administrator processing compatibility; no historical kind or snapshot is rewritten.

## Public and member actions

- `public_home({})` → `{settings,categories,request_categories,products,gx_classes,posts,terms,form,forms,form_programs}`. Only published/in-window posts, active categories and active reviewed catalog; no account/payment/member data. Bank account excluded here; `settings.transfer_available` indicates a configured bank. GX includes `remaining_seats` accounting for protected reported/held reservations.
- `my({})` → `{profile,passes,applications,requests,payments,profile_changes,settings}`. Null profile for an unlinked authenticated account. Personal responses are never cacheable. Settings include bank fields only for a verified member or own pending application.
- `activate_invite({code})` → `{profile}`. Uses existing authenticated, email-confirmed Supabase Auth account. Code is 64 random hex characters, one use, expiring, optionally email-bound. Admin must first verify the member in person. Never put the code in the common QR.
- `application_submit({idempotency_key,kind:'renewal',product_id?|gx_class_id?,payment_method:'transfer'|'card',desired_start_date?,payer_name?,consents:[termId],form_values:{},signature_path?,student_name?,guardian_consent?:boolean,expected_amount,expected_catalog_updated_at,expected_form_id})` → `{application,duplicate?:true}`. UUID idempotency key, exactly one product/class. This legacy authenticated endpoint requires an already linked and verified member profile; it never creates a profile from applicant input. `new`, missing and invalid kinds are rejected for new submissions. Terms and amount always come from DB. Every applicable `privacy` and `rules` term must be individually included in `consents`, even with `required=false`. Same pending selection returns its prior application. Frontend supplies displayed price/catalog timestamp/form ID; server rejects stale values. Guardian terms required only for child GX. New `cash` submissions are rejected; stored historical cash records are preserved.
- `request_submit({idempotency_key,category_id,title,body,location?,photos:[],item_name?,quantity?})` → `{request}`. Verified profile only. No internal notes in member response.
- `payment_report({id,payer_name?})` → `{application}`. Only own allocated transfer application; sets `payment_status='reported'`, never creates a payment/pass.
- `profile_change({changes:{name?,building?,unit?,phone?}})` → `{item}`. Queues admin review, never overwrites profile.

## Admin actions

Existing `public.app_admins(active=true)` remains the sole administrator authority. This existing project is one center; no new global role is created.

- `admin_list({entity,search?,status?,category_id?,location?,date_from?,date_to?})` → `{items}`. Entities: `profiles`, `passes`, `applications`, `payments`, `requests`, `posts`, `products`, `gx_classes`, `categories`, `terms`, `forms`, `profile_changes`, `audit`, `settings`, `admins`. Requests include `internal_notes` only in this admin action; applications/requests include a nested `member`. Admins returns `id,user_id,display_name` for approved administrators. Lists are capped at 1000 most recent records; requests apply category/location/KST-date filters before the cap.
- `admin_save({entity,data})` → `{item}`. Supported entities and fields below; use `id` for update. Settings accept either data fields directly or `data.data` object. Terms and forms are immutable versions: saving creates a new version; prior snapshots stay unchanged.
- `admin_action({entity:'applications',id,operation:'approve'|'hold'|'cancel'|'external_done'|'assign_seat',actual_amount?,paid_at?,payment_note?,note?,expected_updated_at?,expected_start_date?,expected_end_date?})` → `{item}`. Approve requires exact `actual_amount` matching snapshot, verified resident and valid allocated GX seat; recalculates period using KST approval date/latest pass. Displayed expected dates/timestamp reject stale approval. Amount mismatch must be held, not silently changed. Retrying approval returns original result. Paid cancellation becomes `refund_required`; payment history remains. Hold protects GX seat pending review. `assign_seat` allocates oldest waiting applicant under class lock.
- `admin_action({entity:'requests',id,operation:'update',status,reply,internal_note?,assignee?,action_photos?:[]})` → `{item}`. Internal note goes to separate private table. Status: `received`, `reviewing`, `in_progress`, `completed`, `needs_info`, `held`, `declined`. Declined requires reply. No automatic internal issue/public post creation.
- `admin_action({entity:'profiles',id,operation:'verify'|'suspend'})`. Verify sets resident verification and approval, not phone verification.
- `admin_action({entity:'profiles',id,operation:'import_pass',product_id,start_date,end_date,note})` → `{item:pass}`. Records a verified member's documented existing entitlement, with `source:'import'` and no fabricated payment. Requires evidence note and rejects overlapping active/suspended passes. Intended solely for moving existing records, not selling unpaid extensions.
- `admin_action({entity:'passes',id,operation:'suspend'|'resume',note})` toggles operational hold without changing dates; no automatic extension of suspended rights.
- `admin_action({entity:'profile_changes',id,operation:'approve'|'reject',note?})`.
- `issue_invite({member_id,email?,expires_hours?:24})` → `{code,expires_at}`. Expires in 1–24 hours. New invite invalidates old unused invites for that profile. Code returned once; only hash stored.
- `import_members({rows:[{name,building,unit,phone}],commit:false|true,confirm_duplicates?:true,idempotency_key?:UUID})` → `{preview:[{row,index,errors,duplicate_candidates}],inserted?}`. Max 500 rows. Commit revalidates all rows and aborts batch on any invalid value; duplicates need explicit acknowledgement, always insert distinct pending profiles. Preview does not insert members. The UI supplies one idempotency key per parsed CSV batch; replay returns the original result without duplicate imports, and a different file with the same key is rejected.

## Data fields

- profiles: `id,name,building,unit,phone,resident_verified,phone_verified,approved,active,user_id,created_at`. Admin save cannot set `user_id`/`phone_verified`. Verify via explicit action.
- products: `id,name,facility,duration_days,price,effective_from,sort_order,active,reviewed,calculation_method:'days'`. Facility is stable string identifier, including `fitness`, `golf`, `fitness_golf`. Initial 12 photographed products disabled/unreviewed. Changing a facility on a used product is rejected.
- gx_classes: `id,name,class_name,weekdays:[1..7],start_time,period_start,period_end,price,capacity,registration_start,registration_end,priority_start,priority_end,payment_due_hours,waitlist_enabled,status:'inactive'|'open'|'closed'|'suspended',reviewed,is_child,guardian_terms`. All timestamps ISO with timezone; period dates YYYY-MM-DD. Must fill capacity/period/registration/payment deadline before opening. Initial 11 classes disabled/unreviewed.
- categories: `id,kind:'board'|'request',name,sort_order,active`.
- posts: `id,category_id,title,body,location,progress_status,action_date,photos:[],before_photos:[],after_photos:[],pinned,status:'draft'|'published'|'archived',publish_at,expires_at`. Photos are private storage paths. Published status requires `preview_confirmed:true` on save. Content is plain text, never executable HTML.
- terms: `id,title,body,required,kind:'privacy'|'rules'|'guardian',program:'common'|'fitness_golf'|'gx',approved,active,version`. Requires applicable approved privacy and program rules. Application privacy/rules consents remain mandatory regardless of `required`; other conditional requirements are unchanged. A new save deactivates the supplied prior ID and active versions of the same program/kind/title; snapshots preserve original text.
- forms: `id,program:'common'|'fitness_golf'|'gx',title,signature_mode:'none'|'new'|'always',fields:[{key,label,type:'text'|'textarea'|'select'|'checkbox',required,help,options:[]}],active,version`. Only extra fields; reserved authentication/payment/core keys rejected. Save creates an immutable next version within the program and only deactivates that program's previous active form.
- settings: `center_name,contact,main_title,subtitle,intro,menu_renew,menu_requests,menu_my,menu_board,applications_enabled,requests_enabled,bank_name,bank_account,bank_holder,transfer_guide,card_guide,request_guide,privacy_purpose,privacy_items,privacy_retention,signature_enabled,photo_limit`. Default collection switches off. Activation requires privacy purpose/items/retention and approved privacy terms; applications also approved rules and active form. No settings can disable auth or payment checks.
- application: `id,application_no,member_id,kind,product_id,gx_class_id,product_snapshot,amount,payment_method,payer_name,desired_start_date,previous_start_date,previous_end_date,proposed_start_date,proposed_end_date,final_start_date,final_end_date,application_status,payment_status,pass_status,external_status,reservation_status,reservation_expires_at,consents_snapshot,form_snapshot,form_values,student_name,guardian_consent,signature_path,created_at,processed_at,processed_by`. Status columns remain distinct. `application_status`: `new|pending|needs_review|completed|cancelled|refund_required`; `payment_status`: `awaiting|reported|confirmed|refund_required`; `pass_status`: `pending|applied|needs_review|revoked`; `external_status`: `pending|done`; `reservation_status`: `none|reserved|waitlisted|confirmed|expired|cancelled`.
- passes: `id,member_id,application_id,facility,product_name,start_date,end_date,status:'active'|'suspended'|'revoked',gx_class_id`. Never issued before recorded admin-confirmed payment.
- requests: `id,request_no,member_id,category_id,title,body,location,photos,item_name,quantity,status,reply,action_photos,assignee,created_at,updated_at`; internal notes excluded from member responses.

## Private files

Bucket `member-service-files` is PRIVATE; allowed JPEG/PNG/WebP, max 8 MiB (client should resize/strip EXIF). Paths: `requests/{auth.uid()}/{randomUUID}.jpg`, `applications/{auth.uid()}/{randomUUID}.png` for signature, `posts/{postUUID}/{randomUUID}.jpg` for admin-uploaded board photos. No personal names in paths. Upload confirmed authenticated user own path only (or approved administrator). Request uploads require verified active membership, requests enabled, and an active approved privacy term; signature uploads require applications enabled. Administrators retain uploads for existing request handling while member collection is closed. Members are limited to 100 uploaded objects per hour. Board upload admin only. Files must exist before storing references. Use `createSignedUrl(path,60)` for display; do not use `getPublicUrl`. Public users may sign/read only images explicitly referenced by a currently published/in-window post. Existing signed URLs expire within the requested 60 seconds after unpublishing. Internal action photos use `requests/{adminUserId}/{randomUUID}.jpg`, and become visible only to request owner via RPC/file policy. Client file mutation/deletion is denied to preserve reviewed evidence; removing a reference hides the image, while retained objects require an audited operator cleanup.

## Rollout

Apply only `supabase/member-service.sql`, never setup.sql. It is additive and seed inserts use stable IDs + ON CONFLICT DO NOTHING. Existing operational tables/auth/policies untouched. New tables have RLS, zero direct client mutation grants; all writes go through validated RPC. Disable collection using settings switches; preserve existing data and old pages. Test using isolated DB harness before approved production migration.
