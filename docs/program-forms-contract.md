# 프로그램별 신청서 계약

`supabase/program-forms.sql`은 이미 운영 중인 `member-service.sql`과 `guest-service.sql` 뒤에 적용하는 재실행 가능한 구조·함수 마이그레이션입니다. 회원·신청·결제·기존 동의/신청서 스냅샷·접수 스위치를 변경하지 않습니다. 원본 문서 초안은 별도 `program-form-content.sql`로 적용하며 운영자 승인과 수집 목적·항목·보유기간 확인 전까지 접수는 OFF로 유지합니다. 신규 설치는 최신 기본 SQL 두 파일을 적용하면 같은 구조가 됩니다.

## 공개 설정과 선택

`member_service('public_home', {})`의 기존 결과에 아래 필드가 추가됩니다.

- `forms`: 활성 양식 목록. 각 양식은 `id`, `program`, `title`(최대 120자), `signature_mode`, `fields`, `version`을 포함합니다.
- `form_programs`: 특정 양식 이력이 있는 프로그램 목록. `fitness_golf`, `gx` 중 해당 값만 반환하며 비활성 초안의 내용은 공개하지 않습니다.
- `terms`: 기존 활성·승인 약관 목록에 `program`이 추가됩니다.
- `form`: 기존 클라이언트용 활성 `common` 양식을 계속 반환합니다.

`product_id`를 선택하면 프로그램은 `fitness_golf`, `gx_class_id`를 선택하면 `gx`입니다. 서버는 입력된 임의 프로그램보다 선택 상품의 실제 종류를 기준으로 검증합니다.

선택 프로그램의 활성 양식을 사용합니다. 해당 프로그램 양식 이력이 **전혀 없을 때만** 활성 `common` 양식으로 호환합니다. 특정 양식이 존재하지만 비활성화되면 해당 프로그램 접수가 중단됩니다. UI 역시 `form_programs`를 사용해 같은 규칙을 적용해야 합니다.

신청 약관은 `common`과 선택 프로그램을 합쳐 적용합니다. 건의·민원은 `common` 개인정보 약관만 적용합니다. 어린이 GX에만 보호자 약관을 추가로 요구합니다. 해당 양식의 `program`에 승인된 이용규정이 있어야 접수할 수 있습니다. 필수 동의·추가 입력·양식 ID·상품 금액 및 버전 검증은 서버가 수행합니다.

## 서명

- `none`: 서명 업로드 및 서명을 포함한 제출을 받지 않습니다.
- `new`: 신규 신청은 필수, 재등록은 선택입니다.
- `always`: 신규·재등록 모두 필수입니다.

특정 프로그램 양식은 `signature_mode`가 최종 기준입니다. 레거시 `common` 양식만 모드가 `none`이며 이전 `settings.signature_enabled=true`이면 `new`로 해석합니다. 공개 `forms`와 저장되는 `form_snapshot`에는 이 유효 모드가 들어갑니다.

비로그인 서명은 기존 private photo capability를 사용합니다. 준비 후 규정·접수 설정이 철회되면 업로드와 제출을 차단합니다. 기존 인증 회원의 Storage 서명 업로드 역시 개인정보 설정, 유효 양식, 승인된 개인정보 안내와 해당 프로그램 이용규정이 있어야 가능합니다. 관리자 자료 처리 권한은 그대로 유지합니다.

## 비로그인 프로그램 고정

```js
guest_service('prepare', {
  kind: 'application',
  program: 'fitness_golf' | 'gx',
  phone,
  consents: [/* common + 선택 프로그램의 개인정보 동의 ID */],
  honeypot: ''
})
```

결과에 `program`이 포함되고 티켓에 고정됩니다. 헬스·골프 준비 티켓으로 GX를 제출할 수 없습니다. 프로그램 변경 시 새 티켓을 준비합니다. 필수 약관은 최종 제출 때 다시 검사하며 `expected_form_id`는 선택 프로그램 양식 ID입니다.

`request` 준비는 항상 `common`입니다. 과거 프로그램이 없는 임시 티켓과 `common` 준비 요청은 특정 양식이 전혀 없는 기존 설치에서만 호환됩니다. 특정 양식을 도입한 뒤에는 과거 임시 신청을 다시 작성해야 합니다. 이미 최종 접수된 건의 조회·관리자 처리는 영향을 받지 않습니다.

## 관리자 버전 및 현금

`admin_save('forms')` 데이터에 `program`, `title`, `signature_mode`가 추가됩니다. 프로그램별 활성 양식은 최대 하나이며 버전도 프로그램별로 증가합니다. 저장은 새 버전을 만들고 기존 ID를 전달하면 그 버전을 비활성화합니다. 기존 버전의 프로그램을 다른 프로그램으로 이동할 수 없습니다.

`admin_save('terms')` 데이터에 `program`이 추가됩니다. 제목이 바뀌어도 기존 ID를 함께 전달하면 이전 버전은 비활성화됩니다. 같은 제목의 다른 프로그램 약관은 유지합니다. 과거 신청의 양식·동의 내용은 다시 쓰지 않습니다.

`payment_method`와 결제 기록 `method`는 `cash | card | transfer`입니다. 현금도 접수만으로 결제 완료나 이용권을 만들지 않습니다. 직원이 실제 결제를 확인하고 기존 승인 트랜잭션을 실행해야 결제 기록과 이용권이 생성됩니다. 현금/카드에 계좌정보를 표시하거나 `payment_report`를 허용하지 않습니다.

## 검증

`node tests/program-forms.mjs`는 격리 PostgreSQL에서 배포 이전 커밋 `3003f96`의 실제 SQL로 시작해 업그레이드를 두 번 적용합니다. 원본 콘텐츠 seed 재실행, OFF 스위치·스냅샷·관리자 권한 보존, 레거시 호환, 프로그램 변경 방지, 약관과 서명 강제, 서명 수집 중지, 현금 최종 승인, 프로그램별 버전 및 비활성 동작을 검사합니다. 운영 DB에는 연결하지 않습니다.
