# 비로그인 회원 접수 운영 안내

회원 화면은 별도 계정 없이 이용합니다. 기존 관리자 계정과 승인 관리자 목록은 그대로 사용합니다. 회원용 Auth 가입, 익명 Auth 사용자 생성, 이메일 인증, 비밀번호, 초대코드, 인증 복귀주소 설정은 필요하지 않습니다.

## 접수 시작 전

사용자 요청에 따라 웹 화면과 DB만 배포하고 신청·건의 접수 스위치는 모두 꺼 둡니다. 관리자가 개인정보 수집 목적·항목·보유기간, 승인된 동의문·이용규정, 신청서, 상품 요금·기간, GX 일정·정원·접수기간을 확인한 후 필요한 접수 스위치를 엽니다. 계좌이체는 실제 은행·계좌·예금주가 설정되어야 합니다.

접수가 닫혀 있으면 비로그인 신청 화면에서 준비 안내를 표시하고 개인정보 입력·제출을 막습니다. 서버도 준비·제출·회원 사진 업로드를 거부합니다. 기존 접수 확인과 관리자의 후속 처리는 유지합니다.

## 회원 이용 흐름

1. 공통 QR 또는 `/members`에서 빠른 연장이나 건의·요청을 선택합니다.
2. 이름·동호수·연락처와 신청 내용을 입력하고 승인된 안내에 동의합니다. 입력한 개인정보로 기존 회원정보를 자동 조회하지 않습니다.
3. 접수 완료 화면에서 접수번호와 64자리 비공개 확인키를 복사하거나 확인서 파일로 저장합니다. 이 키는 해당 접수내용·사진·답변을 열람할 수 있는 비밀이므로 타인에게 공유하지 않습니다.
4. `/members/my`의 접수 조회에서 접수번호와 확인키를 함께 입력합니다. 키를 잃어버리면 안내데스크에서 본인 확인 후 안내받습니다. 전화번호만으로 조회·키 복구를 허용하지 않습니다.

확인키는 URL, QR, 브라우저 영구저장소에 넣지 않습니다. 화면을 닫거나 새로고침하면 다시 입력해야 합니다. DB에는 키 원문 대신 해시만 보관합니다. 접수 완료는 회원 승인·결제 완료·이용권 연장 완료를 뜻하지 않습니다.

## 관리자 처리

- **신청·수납 관리 → 회원 연결 대기(비로그인)**: 신청자가 입력한 정보와 기존 회원 후보를 현장에서 확인한 뒤 직접 연결합니다. 신규 회원은 미승인 상태로 등록하고, 입주민 확인·승인을 별도로 처리합니다.
- 회원 연결 후 수납 신청으로 전환합니다. 전환 자체로 이용권은 생기지 않습니다. 기존 결제 확인 절차에서 실제 결제금액·결제일 등을 확인해야 이용권에 반영됩니다. 중복 전환과 중복 승인은 동일 기록으로 처리합니다.
- GX는 비로그인 접수 시 자리를 확정하지 않습니다. 관리자가 회원 연결 후 전환할 때 정원·우선접수 조건을 확인하여 자리 또는 대기순번을 배정합니다. 배정 전과 대기 중에는 입금 안내를 표시하지 않습니다.
- **건의·민원 관리**: 비로그인 접수는 본인 확인 전 자료로 표시됩니다. 상태·회원 답변·조치 사진을 저장할 수 있으며 내부 메모는 회원 조회에서 제외됩니다.

## DB 적용 및 검증

기존 `member-service.sql` 적용 완료 후 `supabase/guest-service.sql`을 트랜잭션 단위로 추가합니다. 네 개의 비공개 `ms_guest_` 테이블과 `guest_service` RPC를 추가하고, 기존 신청에 비로그인 접수 출처를 연결합니다. 기존 점검·비품·민원 기록, 승인 관리자 목록, 공유 프로젝트의 다른 서비스 및 Auth 설정은 변경하지 않습니다. 운영 설정과 기존 가격·동의문을 덮어쓰지 않습니다.

모든 회원서비스 테이블은 RLS를 사용하고 `anon`·일반 로그인 역할에 직접 테이블 읽기·쓰기 권한을 주지 않습니다. 공개 RPC는 접수 준비·제출 및 확인키가 일치하는 해당 접수만 처리합니다. 관리자 동작은 기존 `is_app_admin()`을 검증합니다. 사진은 비공개 DB에 저장하고 접수 범위 검증 후만 전달합니다. JPEG/PNG/WebP만 허용하고 장당 512KiB, 회원 사진 최대 3장, 서명 1장, 관리자 조치 사진 3장, 전체 50MiB 한도를 적용합니다. 프런트엔드는 이미지 재인코딩으로 메타데이터를 제거합니다.

접수 시도에는 연락처별·전체 횟수 제한과 짧은 준비 유효기간이 있습니다. 자동화된 대량 요청에는 접수가 일시 제한될 수 있습니다. 사진 한도에 도달하면 사진 없이 접수하거나 센터에 문의하도록 안내합니다. 보유기간 경과 자료의 실제 파기는 별도 승인된 운영 절차로 수행하며 자동 삭제를 실행하지 않습니다.

회귀 검증은 `npm test`, `npm run test:db`, `node tests/backend-security.mjs`, `node tests/guest-service.mjs`를 사용합니다. 운영에는 가짜 회원·결제·건의를 만들지 않습니다. 배포 후 접수 비활성·개인 테이블 접근 차단·관리자 메뉴 조회를 읽기 위주로 확인합니다.

## 중단·복구

문제가 있으면 관리자 설정에서 접수 스위치를 끄고 웹 배포를 검증된 이전 버전으로 되돌립니다. 접수·결제·사진 기록을 지우거나 이전 초기화 SQL을 재실행하지 않습니다. 비로그인 전환 후 생성된 수납 신청은 `submitted_by`가 비어 있고 원본 접수 ID가 연결되어 있으므로 과거의 `submitted_by NOT NULL` 제약을 무조건 복구하면 안 됩니다. 기존 범위별 로컬 백업은 공유 DB 전체 시점 복원이나 Storage 원본 백업이 아닙니다.
